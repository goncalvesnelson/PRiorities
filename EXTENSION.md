# PRiorities Chrome extension

A local prototype for reviewing GitHub pull requests with Codex or Claude Code and your existing CLI login. It reads the PR you open, explains its behavior in a Guide with paired before/after code and section-focused folding. Chrome starts a local helper when needed. No API key, running HTTP server, or GitHub token is required.

## Load it

Build the extension and register the helpers with Node 24 and at least one installed CLI:

```sh
git clone https://github.com/goncalvesnelson/PRiorities.git
cd PRiorities
npm ci
npm run build:extension
npm run install:cli-host
```

The installer registers every supported CLI it finds on PATH. To use Codex, check `codex login status` and sign in with `codex login`. To use Claude Code, check `claude auth status` and sign in with `claude auth login`. The helpers use those logins without reading or copying credentials. After installing, Chrome launches the selected helper automatically; no terminal process needs to stay open. Re-run the installer when adding a CLI to an existing installation.

After pulling changes, run `npm ci`, `npm run build:extension`, and `npm run install:cli-host`, then choose **Reload** in `chrome://extensions` and refresh the PR page. Reloading or disabling the extension stops its UI in already-open pages and restores GitHub’s diff; refresh the page after enabling or reloading it to reconnect. Completed saved reviews remain available, but unfinished analyses do not survive an extension reload. The installer copies the native helper; reloading Chrome alone does not update that copy, and an older helper sends no live model progress. If you use `CODEX_HOME` or `CLAUDE_CONFIG_DIR`, set the same directory when rerunning the installer. For a fresh installation:

1. Open `chrome://extensions` in Chrome.
2. Turn on **Developer mode**, choose **Load unpacked**, and select this folder:

   `PRiorities/extension` inside your checkout

3. Open **PRiorities** from Chrome’s extensions menu, choose **Codex** or **Claude Code**, and choose **Check connection**, then **Save settings**. It should report the selected CLI's login.
4. Open a PR's **Files changed** tab, refresh it if it was already open, then choose **Analyze PR** in the PRiorities panel. Guide renders unified before/after code independently of GitHub’s Unified or Split setting.

Choose any PR you can read. Fresh analysis uses the current captured PR; no prepared review is bundled.

Selecting commits in GitHub changes the analysis scope. On a commit-range diff, **Analyze range** reads every file in that comparison, and the toolbar shows its base and head commits. File classifications, the final check, source context, and saved reviews all use that pair. The PR description and linked issues still provide intent, but may describe work outside the selected range. Navigation to Checks and reloads reconnect to the same range analysis. Changing the comparison’s commit pair clears the current analysis session; completed reviews remain cached separately by commit pair.

Settings loads the model catalog from your installed CLI. Choose a model and one of its supported reasoning effort levels, then **Save settings**. **Custom model ID…** lets you enter a specific release, including older versions; for a custom ID absent from the catalog, the CLI checks effort support when analysis starts. Each CLI has separate model and effort preferences. **Files classified at once** (default 6, 1–10) applies to both CLIs; each file runs its own CLI process, so choose fewer if the CLI reports rate limits. Changing it never invalidates saved reviews. **Maximum changed files to analyze** (default 100, 1–300) stops a larger PR during capture, before its remaining diffs are fetched or any code is sent; the message gives the PR’s file count and points to Full diff. Changing the limit never invalidates saved reviews. Reviews use the selected account’s allowance.

**List deleted files without sending their contents to the AI** is off by default. When on, files deleted outright (GitHub’s removed files on the Changes page; a single hunk ending in `+0,0` elsewhere) are not read where GitHub allows skipping them, and their contents never enter the captured snapshot or a model request. They don’t count toward the file limit, so a PR of 14 changed and 115 deleted files can be analyzed with the default limit. Files are not classified; the PR review receives only their paths and deleted-line counts as an evidence limit. Their headers and the file list show **AI skipped · deleted**, the coverage caption counts them separately, and Guide lists them in one collapsed group with their deleted-line counts. Full diff still shows them. There is no per-file **Review anyway** for deleted files: turn the option off and analyze again. Up to 3,000 changed files in total can be read, GitHub’s own Changes page limit. Reviews made with the option on are saved separately from reviews of the same PR made with it off.

The PR panel displays the CLI, model ID, and effort used by the analysis. Catalog selections use resolved model IDs and explicit effort where supported. A custom model with **Model default** leaves effort to the CLI and is labelled accordingly. A running analysis keeps its original CLI, model, effort, concurrency, and review preferences through retries and **Review anyway**, even if you change Settings. Model discovery makes no analysis requests. [Codex model catalog](https://learn.chatgpt.com/docs/app-server), [Claude Code CLI reference](https://code.claude.com/docs/en/cli-reference).

When you return from Settings after changing the CLI, model, or effort, **Analyze PR** appears in the toolbar once the current analysis is idle. A notice identifies the settings it will use. The existing review keeps its original model label and explanations until you choose to analyze again; changing settings does not start an analysis. Returning to the review’s original settings moves the rerun action back into **More actions**.

## Configure what stays visible

In **Settings → What should stay visible?**, choose **Selective**, **Balanced**, or **Thorough** focus. Selective concentrates on consequential decisions and the code needed to assess them; Balanced asks for more implementation and test context; Thorough asks for more distinct changes worth inspecting. These guide the model’s judgment without line, excerpt, or decision quotas. Important changes should remain visible with sufficient context; lower-priority details should be deferred for a stated reason. The model is instructed to check for both omitted important evidence and unnecessary excerpts.

**Always keep these change types visible** prevents PRiorities from folding edits with the selected classifications, regardless of the model’s priority or excerpts. It applies to analyzed files and preserves selected change types identified by either the file classification or the final PR review. Validation retains these types even if the final review removes them. The final review can resolve unknown classifications using the combined evidence. Within a section’s displayed files, its assigned changed blocks and selected context stay visible, as do unresolved edits and your always-visible types. Visible edits owned by another section identify that section and explain why they are shown. GitHub discussions remain in Full diff. Generated and machine-maintained files still need **Review anyway** before analysis.

**Always keep these files visible** lists paths that never fold, whatever the model decides. Enter one path per line; it matches at any depth, so `go.mod` covers `services/api/go.mod`. End a line with `/` to cover a whole folder, such as `migrations/`. The default list covers common dependency manifests, `Dockerfile`, `.github/workflows/` and `migrations/`; edit it to match your repositories. Protected files are still analyzed and explained, and their captured code stays expanded, with protected context and foreign edits labelled.

**Advanced: edit analysis prompts** exposes the full classification and prioritization instructions. Classification labels every edit; prioritization chooses the decisions and source excerpts to show. Classification runs once per file; prioritization runs once for the whole PR. Reset either editor to restore its built-in prompt, then choose **Save review preferences**. The extension still adds source-handling rules, validates results, and enforces visibility controls. Custom instructions cannot disable those checks.

Preferences apply to new analyses and are included in saved-review fingerprints. Changing focus, always-visible types, or prompts requires a fresh analysis; completed results already open in a tab retain their original preferences.

## Review a change

PRiorities appears in GitHub’s **Files changed**, **Changes**, and individual commit diffs. Its panel and Guide are hidden on Conversation, the Commits list, and Checks.

Analysis captures the selected comparison once, then classifies up to six files concurrently by default (see **Files classified at once** in Settings), one session with the selected CLI per file. Progress appears beside each loaded file and in the panel’s file progress list. Files show only their status while classification runs: no explanations appear and the diff stays expanded until review decisions across those files arrive. **Retry file** reruns only that file’s classification against the same captured commits.

While analysis runs, one line in the PRiorities toolbar shows its steps (**Copy**, **Label** with files labelled, **Write review**, **Check**) and how long the current step has taken, measured from when the extension started it, so reloads and reconnection keep the count. While files are labelled it names the running files and their labelled blocks. While the PR review is written, Claude Code reports how many blocks the answer has labelled and the latest section title; Codex only reports that it is reasoning, because its CLI does not stream partial answers. Hover **Label** for the labelled change types, and **Write review** for a rough estimate: it appears only after three earlier reviews with the same CLI and model, scaled by changed lines. The extension keeps the last 20 review durations in local browser storage for this. Model text is shown as plain text and never affects the result or its validation. If the GitHub tab is in the background when a review finishes, fails or needs a retry, its title starts with “✓ Ready” or “⚠ Needs attention” until you return to it.

GitHub-marked generated files, known lockfile names and Xcode `.pbxproj` project files are excluded from AI analysis by default. Their headers and the file progress list identify them as skipped by the AI, with a **Review anyway** button. Excluded files receive no standalone model call. After an assessment is available, their captured changes remain accessible from the file list, labelled as not analyzed. A changed `go.sum` can still be sent as supporting evidence when a reviewed Go file is in the same directory; other excluded contents stay out of model requests. A PR with only these files makes no model calls until you choose a file. Skipping a file does not change GitHub's own collapsed-file state or your review checkmark.

**Review anyway** adds that file to the queue using the same captured commits. It works while other files run or after they finish. Completed classifications are kept; review decisions for the PR are chosen again with the newly included file. The previous Guide is withdrawn immediately. Full diff remains accessible until the replacement review succeeds, including if it fails or is cancelled. If that review is already running, it is cancelled and replaced after the requested file is classified.

Once all included text files are classified, one session reads the entire captured comparison with those classifications, connects related changes across files, and chooses the review decisions. Guide becomes available only when this review succeeds. A failed review keeps the classifications and offers **Retry review decisions**. Each file classification and the final review have separate ten-minute deadlines; there is no deadline on total analysis duration. The selected CLI manages its own network retries; the extension does not automatically repeat failed analysis.

This uses one session per included text file plus one PR review (five sessions for four ordinary text files and one excluded lockfile). Requesting that lockfile afterward adds two sessions: its classification and a new PR review. Three-way concurrency shortens classification; it does not promise lower total latency or usage.

The toolbar shows AI progress and your GitHub Viewed count, with the selected model and effort underneath. Completed, reopened and reconnected reviews open in **Full diff**, so you can survey GitHub’s complete diff first. **Guide**, one click away, explains behavior in comprehension order: prerequisites before their uses, with related implementation, callers and tests together. A compact overview gives the PR summary beside a numbered list of sections, each marked Review or Supporting, so urgent decisions remain easy to find. The overview states how many of the PR’s files the Guide covers and how many generated or machine-maintained files were not analyzed. Under each section title, a caption compares the section with the whole PR: its files out of all files, its changed lines out of all changed lines, and how many lines are currently folded in its code (updated as you open folds). Folded lines and other sections’ changes stay one click away, and Full diff always shows everything. Each section starts with **Files in this section**, showing the section’s own +additions/−deletions and your **Reviewed by you** state; a file name jumps to its code. It then explains **Before**, **After** and **Why it matters**, and lists its **Review questions** (supporting sections may have none). **Evidence limits** and **Change classifications** start collapsed; **Analysis details** holds provenance, cache status and capture limitations. On wide screens the explanation stays pinned beside the code while you scroll, scrolling within itself when taller than the window, with **Section N of M**, **Previous**, **Next** and **Full diff** at its top. On narrow screens it appears above the code and that navigation row stays pinned. **Previous section** and **Next section** follow the code. Each file’s one-row header stays pinned while you read it: name, directory, the section’s +/−, **Reviewed by you**, **Show in diff**, **Before** and **After**. Folded code reads *N unchanged lines*, or *N other lines* with a link to the section its changes belong to. Model text supports only `code`, **bold** and “- ” lists; anything else, including HTML, is shown as plain text.

Each section shows one panel per participating file, with deletions and additions together in original diff order. Every selected excerpt carries a short note, shown as a heading directly above the changed block or line where that excerpt starts; overlapping excerpts show their notes together above the combined run. A file you mark Reviewed collapses to its header; **Show code** expands it, and unchecking Reviewed shows it again. Collapsing never changes GitHub’s Viewed state, and expanding shows all of the file’s visible code, including unresolved and protected changes. **Fold other code** starts enabled: the section’s assigned edits and selected context remain open. If an excerpt intersects a changed block, the whole block stays together. Unresolved edits, always-visible types and protected files also stay open; changes belonging to another section carry its link and the reason they are visible. Other rows fold into expandable runs with links to their owning sections. Turning the checkbox off exposes all captured code in these files. Captured source outside the diff is labelled separately; unavailable ranges are identified rather than filled in. Code uses GitHub’s own syntax highlighting when GitHub supplies it. Highlighting is display-only and never sent to the model; a line whose highlighting markup contains anything other than GitHub’s syntax spans, or does not match the captured text, is shown plain. A supporting section still shows its assigned changes when it has no excerpts.

**Full diff** restores GitHub’s mounted diff, order, comments, drafts and controls. **Show in diff** switches there and attempts to locate the file and matching row. GitHub may need to load or expand a file first; split layouts may only support a file-level jump. **Before** and **After** open the file’s source at this commit separately and does not include review discussions. Guide does not capture or duplicate comments. Switching views preserves the selected section and expanded runs and makes no model calls. Arrow keys, Home and End work in the view control. **More actions** (⋯) contains Settings and **Run fresh review**.

The file list retains captured GitHub order. Each file links to every section explaining its changes, plus separately identified evidence-only references. Files without an explanation remain reachable. Completing a file does not hide its code or remove it from a multi-file explanation.

Analysis starts only when you click **Analyze PR** or **Run fresh review**. **Cancel** stops capture or terminates every active local review process and cancels queued files, retaining completed classifications. Retry cancelled files individually to continue. A changed revision cancels the queue, restores Full diff, and requires fresh analysis.

Once capture finishes, unfinished analysis continues when you switch to Conversation, Checks, or Commits, or reload the page in the same browser tab. Returning to the diff reconnects automatically, restoring file progress, completed explanations, and the original model, effort, and review preferences. It uses the captured evidence without repeating completed classifications. Closing that browser tab ends the session. Leaving during the initial capture interrupts capture; no background analysis has started yet.

The progress control counts completed AI file analyses separately from your GitHub Viewed files and identifies the current phase, cancellation, or failure. Click it to open or close the file list; analysis and reconnection leave the list closed until you request it. Progress updates preserve your choice. Each native file header has a small AI status label: waiting, classifying, classified, ready, skipped, or needing retry. **AI ready** means its review decisions are available, not that you have reviewed it. The file list's **Reviewed by you** checkmark operates GitHub's Viewed control. **To review** includes files not confirmed Viewed, including those explicitly labelled with unknown status; **Reviewed** shows confirmed checkmarks, while **AI needs retry** shows failed or cancelled analyses. All sections remain available in Guide. Pending and failed files keep their code visible.

Use GitHub’s **Viewed** checkbox as you finish reading a file. **Reviewed by you** in Guide file headers, the section file list and the file list operates that same native control, so GitHub manages the saved marker and its own file collapse. Review progress is tracked per file only; PRiorities keeps no checklist of its own. AI completion, navigation, rerunning analysis and clearing the review cache never mark files for you. GitHub removes the Viewed marker when that file changes.

When GitHub has not loaded a file’s Viewed control, its state is labelled unavailable rather than assumed unreviewed; load the file in Full diff to change it. PRiorities observes GitHub’s displayed control and does not independently confirm its server save. Comments, draft reviews and approval remain in GitHub. See [GitHub’s reviewed-file workflow](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/reviewing-proposed-changes-in-a-pull-request#marking-a-file-as-viewed).

## Saved reviews

Completed reviews are saved locally, including their explanations, classifications, and selected code excerpts. The cache uses 100 MB by default; **Settings → Saved reviews** lets you choose 1–1024 MB, view usage, or clear saved reviews. When it fills, the least recently used reviews are removed first. Reducing the limit immediately evicts entries until usage fits. A single review larger than the limit stays available in its tab but is not cached. Browser storage limits can prevent saving without interrupting the review.

On a return visit, **Open saved review** appears when a review exists for the commit pair and selected CLI, model, effort, and review preferences. Opening it captures the current context and checks a SHA-256 fingerprint covering the PR URL, base and head commits, title, description, diffs, captured source, evidence limits, provider, model, effort, review preferences (including custom prompts), whether deleted files were listed without analysis, and cache format version. An exact match restores the review without new model calls. Saved reviews from before the current Guide prompt contract require a fresh analysis; they are not reopened as if generated with the new comprehension and accuracy instructions. Changed context requires **Run fresh review**, even if the commits have not changed; opening an outdated saved review never starts analysis automatically. **Run fresh review** always bypasses the cache.

Only completed PR reviews are cached. In-progress, failed, and cancelled sessions reconnect after navigation or a reload in the same browser tab. They do not survive closing that tab, restarting Chrome, or reloading the extension. A result that finishes while you are away is shown on return. Completed, delivered reviews saved successfully use **Open saved review** on a later reload. File analysis controls are unavailable while a saved review is opening. Generated files remain excluded unless that saved review already included an explicit **Review anyway** request. You can still request an excluded file after reopening a saved review. The cache uses IndexedDB inside the extension and is not synced to another browser or account.

A context mismatch or failed restoration leaves the saved review intact. Cache lookup, storage and validation failures show an error and never automatically start a fresh analysis; they are not reported as context mismatches. The main action becomes **Run fresh review**; **Retry saved review** lets you try capture again without starting model calls. The same failed saved entry stays secondary in that page until a different saved result becomes available or you reload. A temporary source or linked-issue fetch failure can prevent restoration until capture succeeds again, but it does not delete the earlier result. Cancelling a PR review aborts an uncommitted cache write, preserving any earlier saved review.

## What goes to the selected CLI

Each file classification receives that file’s complete captured diff and available surrounding source, and an inventory of included paths. For reviewed `.go`, `go.mod`, and `go.sum` files, captured changes to `go.mod` and `go.sum` in the same directory are supplied as supporting dependency diffs. A checksum diff can be supplied even when `go.mod` did not change. Pairing does not search ancestor directories or establish module ownership; source files deeper in a module receive no dependency diffs from its parent directory. GitHub-marked generated manifests remain excluded until you choose **Review anyway**. These context-only diffs have no edit IDs to classify and are not standalone review targets. No additional source is fetched for this context. The classification does not receive the PR title, description or linked issues, so the author’s framing cannot steer how edits are labelled.

The PR review receives the PR title, description and linked issues, evidence for all included files, related dependency diffs, and the first-pass classifications. It returns a complete revised classification for every reviewed edit. Validation preserves always-visible change types identified by the first pass, even if the PR review omits them; other labels, including resolved unknowns, may change. The resulting inventory drives explanations, unresolved warnings, folding and the saved review. It must account for every edit exactly once and explain any remaining unknowns. A manifest and checksum can confirm dependency metadata; they cannot establish an external library’s runtime behavior or API compatibility.

The PR review also lists, for each reviewed file and side, the line ranges it may cite: the whole file when full source was captured, otherwise only the diff rows. Context-only dependency diffs cannot be selected as review excerpts until you choose **Review anyway**. An excerpt outside the supplied ranges fails validation. Codex sends this evidence to OpenAI; Claude Code sends it to Anthropic. Full before/after source is collected for up to six runtime files, within a size budget. Generated files are omitted from this source collection. Tests and other files remain represented by their diffs.

Generated diffs are captured locally at the start so **Review anyway** can use the pinned snapshot. Their contents stay out of model requests by default, except for a changed Go checksum diff used as supporting context for reviewed Go files in the same directory, whether or not `go.mod` changed. `go.sum` remains skipped as a standalone review and stays expanded until explicitly included. Other generated files still require **Review anyway** before their contents are sent. Capture size limits and completeness checks apply to all files. Detection uses GitHub's generated flag in React diff data plus explicit lockfile names, including `go.sum`, `package-lock.json`, `npm-shrinkwrap.json`, `pnpm-lock.yaml`, `yarn.lock`, `Cargo.lock`, `composer.lock`, `Gemfile.lock`, `poetry.lock`, and `uv.lock`, and the `.pbxproj` extension, whose files Xcode maintains and people rarely read; it does not guess from directory names.

The extension reads up to three same-repository GitHub issues linked from the original PR description, including plain `Fixes #123` references. It includes their titles, URLs, and original descriptions, bounded to 4,000 characters per issue. Later comments and cross-repository issues are not retrieved. **Capture limitations** reports missing or truncated context. There is no cross-repository knowledge-center integration.

The extension stores your selected CLI, each CLI's model and effort preferences, how many files to classify at once, the changed-file limit and deleted-file listing choice, your review preferences and custom prompts, and the local review cache described above. Login credentials remain managed by their respective CLIs. Claude Code support uses its Claude login, not an API key or third-party provider configuration.

Opening a PR or returning to its tab checks the selected CLI connection. Automatic checks share a 60-second cooldown per CLI across all PR tabs, including failed checks; simultaneous requests share one helper. The cooldown survives background-worker restarts through [Chrome session storage](https://developer.chrome.com/docs/extensions/reference/api/storage#session). An idle tab does not periodically launch the CLI. Return checks are skipped while the tab is hidden or capturing the PR. Once capture finishes, returning from Settings reads your choices for the next analysis while the running analysis keeps its original settings. **Analyze PR** and connection checks in Settings bypass the cooldown, so you can retry immediately after signing in. Settings changes are read again when you start a review.

Both native hosts are restricted to this extension’s ID. Each session runs in a private temporary directory. Codex uses a read-only sandbox, ephemeral sessions, and disabled approvals, user configuration, tools, hooks, and personal skill discovery. Claude Code uses safe mode, an empty tool list, no session persistence, no personal settings sources, and an empty strict MCP configuration. Authentication remains available; administrator-managed Claude policies still apply. The helper deletes its temporary instructions, schema, and results after completion or cancellation. It does not change either CLI's global configuration. See [Claude Code safe mode](https://code.claude.com/docs/en/cli-reference) for the managed-policy boundary.

Codex analysis failures are classified from its structured `error` and `turn.failed` events. When Codex exits unsuccessfully without stdout events, the helper also recognizes its startup error for an unsupported option that the helper passed. This matches the CLI error format, including its optional PATH-alias warning, rather than scanning stderr for general error keywords. Other failures without a recognized cause show a generic error; raw CLI output is not displayed. See [Codex JSON event output](https://learn.chatgpt.com/docs/non-interactive-mode).

## Prototype boundaries

- Guide renders captured unified rows independently of GitHub’s diff layout. Full diff retains GitHub’s nodes and review conversations. Progressive loading can delay native file navigation and Viewed updates; unavailable binary or source content is never reconstructed. Live logged-in React virtualization has not been verified by the public-PR interaction spike.
- Capture reads the complete file inventory on GitHub's current Changes page and fetches missing diffs, including large files and generated files that require GitHub’s separate Load diff endpoint. It also follows paginated and deferred classic diffs and checks their total file count. Capture includes whitespace changes and validates paths, line counts, and commit revisions before analysis. It analyzes up to the file limit in Settings (100 by default, at most 300) within a bounded input size; incomplete or truncated diffs stop capture before any analysis starts. On classic diffs with deleted-file listing on, deleted files are recognized only after their diffs load.
- Priorities are model judgments, not proofs of equivalence. Supporting changes remain available and may still require review.
- Each file classification must account for every edit in that file; the PR review accounts for every included edit. Generated exclusions are shown separately from reviewed files. A missing or duplicated edit, an invalid source reference, or a review decision without evidence from its own changed code prevents that result from being applied. Selection follows importance and evidence, including with custom prompts; the extension does not reject or trim a result to meet a line, excerpt, or topic count. Every cited line must exist in the captured source. A failed PR review keeps completed classifications available for retry.
- The extension runs on `github.com`; GitHub Enterprise hosts are outside this prototype.
- The local helper installer targets Google Chrome on macOS. It was developed against Codex CLI 0.156.1 and Claude Code 2.1.283; older versions may lack the required execution flags.
- Input and result sizes are bounded for Chrome native messaging. Oversized results fail visibly instead of applying a partial review.

## Development and verification

Requires Node 24 and Google Chrome installed at its standard macOS path.

```sh
npm ci
npm run verify:extension
```

The verification command builds the extension, then checks the native hosts, background/runtime flows, and installed extension in a temporary Chrome profile. `npm run verify` runs the same suite. Rebuild after edits, rerun `npm run install:cli-host` when the helper changes, choose **Reload** in `chrome://extensions`, and refresh the PR page.

The checks cover both CLI providers, message framing and process cleanup, credential isolation, complete diff capture, per-file classification followed by one PR review, the configurable file classification concurrency, the changed-file limit, deleted-file listing, isolated retry and cancellation, generated-file opt-in, Guide grouping and folding, native discussion preservation, Full diff as the default view, file-level Viewed mirroring, and saved-review invalidation and eviction. They use deterministic fake CLIs plus public or synthetic [GitHub fixtures](test-fixtures/README.md). They do not call a live model or establish classification accuracy.

The earlier standalone prototype and its private PR fixture are not included in this repository. No separate repository checkout is needed to run these tests.

Retryable sessions remain available while their browser tab is open, including while you visit another GitHub subtab. Completed sessions with excluded files also remain available for **Review anyway**. Closing the tab releases the session. Completed cached reviews can be reopened in a later visit.

The [literature notes](review-literature-research.md) record the research behind the review flow, the changes it motivated, and the evaluation still needed. The [Laya assessment](laya-fit-research.md) explains why it has not replaced semantic classification; its dated implementation details describe an earlier prototype version.

## Helper installation and removal

`node install-native-host.mjs` (also available as `npm run install:cli-host` in the source project) registers `com.review_focus.codex` and/or `com.review_focus.claude` in this user’s Chrome `NativeMessagingHosts` directory for the CLIs it finds, and prints the installed paths. It records absolute paths for Node and the selected CLI, preserving stable executable symlinks so CLI updates take effect. Its PATH contains their directories and system directories; it does not copy the installer shell’s PATH. Re-run the installer if those executables move. Run the installer from the repository root.

Removing the extension stops its access to the helpers. To remove the registrations too, delete `com.review_focus.codex.json` and `com.review_focus.claude.json` from `~/Library/Application Support/Google/Chrome/NativeMessagingHosts/`, plus the helper directory at `~/Library/Application Support/Review Focus/native-host/`. The installer prints the registration and helper launcher file paths. This does not sign you out of either CLI or remove the CLIs themselves.
