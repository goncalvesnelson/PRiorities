# Research on focused, contextual code review

Investigated on 2026-09-28 and 2026-09-29; the grouping and ordering papers were re-read in full on 2026-10-12. The extension's central question: can we direct a reviewer to a few consequential decisions, explain the surrounding behavior, and reduce the code they need to inspect?

**Assessment: keep the direction, but treat its effectiveness as an open empirical question.** The literature supports helping reviewers understand changes, connecting related edits, and reducing repetitive presentation. It does not establish that LLM-selected folding is the best interface, or that code omitted by a model is safe to skip. Our strongest next step is to measure consequential omissions on real PRs, alongside time and explanation quality.

The evidence includes controlled experiments, field deployments, surveys, and model benchmarks; these answer different questions. Recommendations below are engineering interpretations, not results demonstrated for PRiorities.

## Search method and limits

The reading was gathered in three rounds. The first searched combinations of “code review”, “LLM”, “context”, “prioritization”, “benchmark”, and years 2024–2026. The second covered code review attention, refactoring-aware diffs, change decomposition, file ordering, LLM review evaluation, and context selection, following references back to older experiments when they tested the interaction more directly. The third covered author framing, industrial risk gating, change decomposition, calibration, and explanation correctness.

Google Scholar queries ([first](https://scholar.google.com/scholar?q=%22large+language+models%22+%22code+review%22&as_ylo=2024), [second](https://scholar.google.com/scholar?q=%22code+review%22+%22attention%22+%22LLM%22&as_ylo=2024)) failed with access errors, so no Scholar result pages or citation counts were inspected. Discovery used web search followed by author manuscripts, institutional repositories, publisher records, and official conference programs. Vendor rankings and secondary summaries did not supply the findings. This is not a systematic or exhaustive literature review.

Publication status follows the publisher or official program where available. An arXiv manuscript's conference template is not treated as evidence of acceptance; where status could not be verified beyond an arXiv record, the work is labelled a preprint. Every figure below was checked against the linked source, and entries say so where only an abstract or publication record was readable. Experimental findings belong to their tested models and datasets; they are not performance claims about this extension. No private PR content entered a search or a model benchmark during this research.

## What the extension does

This is an architectural reading of the current code, not a validation of its review quality. The earlier assessment inspected `fec0b86`; the changes listed after the table have been applied since.

| Component | Observed behavior | What it establishes |
| --- | --- | --- |
| [Capture](extension/github.js), `capturePullRequest()` | Captures the complete supported diff and PR description, up to three linked same-repository issues, and full before/after source for the first six eligible changed files within size budgets. It does not follow callers or retrieve unchanged dependency files. | A bounded evidence package; source outside it remains unknown. |
| [Scheduling](extension/background.js), `classifyFile()` / `reviewPullRequest()` | Classifies files separately, then supplies the included PR evidence and classifications to one PR-wide prioritization request. | Separation of change identification from review selection. It does not demonstrate superiority over provisional file results followed by a final check. |
| [Prompts](extension/review-preferences.js) | Classification sees only code, without the PR title, description or linked issues. It labels mixed edits and distinguishes labels from importance. Prioritization receives intent text, groups decisions across files, requests before/after behavior and reasons, and asks the model to reconsider supporting changes. There are no presentation quotas. | Instructions about desired reasoning; compliance with their meaning remains a model judgment. |
| [Validation](extension/review-data.js), `validateAnalysis()` | Accounts for every edit exactly once, validates source references against the line ranges sent to the model, and requires each review topic to cite its own changed code. | Structural coverage and real source locations. Neither complete semantic coverage nor correct explanations follow from these checks. |
| [Folding](extension/review-ui.js), `createNativeFolding()` | Keeps visible: every changed line in a review decision, selected excerpts, edits classified `unknown` or matching always-show types, and files matching protected paths. Supporting edits and unchanged context can fold. Unmatched rows and discussion controls stay visible. | Reversible presentation with explicit exceptions. A consequential edit misclassified as supporting, outside a protected path, can still lose visibility. |

The context limit is particularly relevant to complex explanations. Selection currently follows file eligibility and position, not the dependency that a review decision needs. Conversely, giving the model every available file would be an untested response to that limitation.

The automated checks use supplied model responses. They establish request flow, evidence handling, and UI behavior; they do not establish better review decisions, fewer missed defects, latency, or cost on real PRs.

### Changes applied from this research

These are engineering responses, not measured improvements:

| Change | Evidence |
| --- | --- |
| Per-file classification no longer receives the PR title, description or linked issues; the PR-wide review still does. | Contextual bias (Alexopoulos et al.); intent context still helps prioritization (ContextCRBench). |
| Changed lines in a review decision never fold, even outside the selected excerpts. Only surrounding context folds. | Delocalized defects (Baum et al.); attention narrowing (Tufano et al.). |
| An editable list of protected paths never folds; by default it covers common dependency manifests, `Dockerfile`, `.github/workflows/` and `migrations/`. | Layered gating (RADAR); per-category policy (AutoCommenter). |
| Each file classification records the symbols every edit defines and uses; the PR review cannot change them. When a definition and its use land in different sections, both sections link to each other. | Definition/use partitioning, and requests to see why code is grouped (Barnett et al.); make grouping explicit (Baum et al., 2017). |
| The grouping rule explains a changed definition inside the section that calls it, instead of in its own earlier section. | Prefer grouping over prerequisite order (Baum et al., 2017); the #5881 reading test, where a split helper made the Guide harder to follow than the full diff. |

Separately, the PR review now receives the exact line ranges it may cite. This addresses a reported failure where one excerpt line beyond a diff hunk rejected the whole review.

### Prompt comparison on two PRs

On 2026-10-12 the rewritten prompts were run against the previous ones on undici #5881 and #5895 with `claude-opus-5-5` at medium effort, using the production prompt builders and validators outside Chrome. A grader who did not know which version wrote each Guide scored accuracy and readability against the captured source.

| | Previous prompts | Rewritten prompts |
| --- | --- | --- |
| #5881 helper kept with its callers | 1 of 2 runs | 3 of 4 runs |
| Readability, out of 10 | 5–8 | 7–9 |
| Materially wrong claims | none | none |

A first rewrite that still allowed a standalone prerequisite section split #5881 in both of its runs, which led to the current grouping rule. Reading without knowing which was which, the project author found the rewritten Guide easier to read, and the grouping fix kept it so. Two to four runs per PR show a direction, not a result, and the comparison does not measure defects found.

## Evidence

### Labelling, decomposing and refactoring changes

**Beyond Summaries: Structure-Aware Labeling of Code Changes with Large Language Models — Weiss et al., May 2026 preprint; conference publication unverified.** The closest match to our staged analysis. A first pass labels changes; a second connects moves, renames, and their attributes across hunks. Its strongest configuration reports 81% per-hunk precision and 84% recall, on only six natural and seven fabricated PRs, mostly Java, totaling 95 hunks. Per-file input usually outperformed both individual hunks and entire patches. The authors describe their taxonomy as "primarily syntactic". Their future work lists semantic and intent-level categories, decomposition of large hunks, and integration with static analysis. The paper contains no reviewer study, so reviewer benefit remains untested. The behavior/mechanical distinction our classifier depends on is exactly the part it leaves open. **Implication:** distinguish change classification from attention selection, preserve mixed and unresolved changes, and group dependent edits. This supports testing the separation, not borrowing its accuracy as our folding accuracy. [Full paper, §§3–6 and appendices A–B](https://arxiv.org/html/2605.26100v1), [publication record](https://arxiv.org/abs/2605.26100).

**RAID: Tool Support for Refactoring-Aware Code Reviews — Brito and Valente, ICPC 2021.** A close predecessor: a Chrome extension augments GitHub diffs with refactoring information and aligned comparisons. Eight developers used it for three months on four Go projects. Median diff churn for moves fell from 14.5 to 2 lines; the tool exposes edits made within the moved code. However, line count and move distance serve as effort proxies, not measured defect-preservation outcomes. Manual checking also found false refactoring detections. **Implication:** try showing the residual change within a move, with navigation to both locations. Refactoring detection alone cannot justify hiding everything. [Paper, §§II–V](https://homepages.dcc.ufmg.br/~mtov/pub/2021-icpc.pdf), [proceedings contents](https://www.proceedings.com/content/059/059496webtoc.pdf).

**Helping Developers Help Themselves: Automatic Decomposition of Code Review Changesets (ClusterChanges) — Barnett, Bird, Brunet and Lahiri, ICSE 2015.** The tool splits a C# changeset into partitions using three relations between diff regions: edits in the same method, a changed definition and its use, and two uses of the same unchanged definition in the changeset. Isolated regions form "trivial" partitions, a structural category rather than a judgment of importance. On 1,000 Microsoft Office changesets, 45% had one non-trivial partition and nearly 42% had more. Twenty change authors, not reviewers, were interviewed about their own changes: 16 called the non-trivial partitions correct and complete, and 14 of those 16 would have moved up to three trivial changes into a partition, so the main error was too little grouping. Of the trivial partitions they confirmed as correct, 10 called them less important, 8 equally important and 2 gave no answer; they included comments and logging, but also internal logic changes such as edits to `if` statements. Participants asked for the partition with "the meat" of the change first, and to see why regions were grouped: "The UI does not tell me how you created the partitions". The often-quoted "95% correct" requirement is one sceptical participant's condition for using the tool, not a finding. **Implication:** being set aside by a grouping step is not evidence that an edit is unimportant, and grouping should be explainable. [Paper, §§III–VI](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/02/barnett2015hdh.pdf).

**The effects of change decomposition on code review—a controlled experiment — di Biase, Bruntink, van Deursen and Bacchelli, PeerJ Computer Science 5:e193, 2019.** Twenty-eight participants, 12 professional developers and 16 students, reviewed one change of about 100 lines in a small Java game with three injected defects. The control group received it as one pull request; the treatment group received two, split by hand into a feature and a refactoring, in GitHub's default order. Decomposition reduced false reports (6 against 1, Cliff's δ = 0.36, p = 0.03, uncorrected for multiple tests) but not detected defects (20 against 17, p = 0.6) or review time. Treatment reviewers took longer to find the second defect, which the authors attribute to switching between the two pull requests. Screen recordings showed more context-seeking, such as opening related classes, which the authors credit for the fewer false reports. Grouping alone does not settle our question, and folding that discourages context-seeking may remove the benefit. [Full paper](https://pmc.ncbi.nlm.nih.gov/articles/PMC7924728/).

**LLM-Driven Collaborative Model for Untangling Commits (ColaUntangle) — Hou et al., 2025 preprint; Atomizer — Zhu et al., ICSE 2026 per its arXiv record.** On 1,612 C# and 14k Java tangled commits, ColaUntangle improves on the best baseline by 44% and 82%. In two C# repositories, 62–71% of sampled commits contained semantically related edits with no explicit data or control dependency. **Implication:** synthetic tangled PRs can supply grouping ground truth, and a dependency-based check alone would miss many real relations. [ColaUntangle](https://arxiv.org/html/2507.16395), [Atomizer, abstract read](https://arxiv.org/abs/2601.01233).

**How Much Can a Behavior-Preserving Changeset Be Decomposed into Refactoring Operations? — Someya et al., ICSME 2025.** On functionally equivalent Java method pairs, an existing refactoring detector explained only 33.9% of changes; 67 new equivalence-preserving operations raised coverage by over 128%. **Implication:** a refactoring detector could confirm some safe edits, but it cannot validate most edits an LLM calls mechanical. [Abstract](https://arxiv.org/abs/2508.11993).

**Understanding Large-scale Codebase Refactoring through Semantic-aware Differencing — Deknop et al., SANER 2024.** Checks trace equivalence on control-flow graphs in an industrial refactoring case. This offers a much stronger kind of evidence than recognizing that code looks moved or renamed, within the technique's supported scope. The institutional record identifies COBOL as the application domain; it is not an immediately transferable JavaScript equivalence checker. [Author's institutional record and manuscript](https://research.dial.uclouvain.be/entities/publication/a6a399c0-5c89-40a5-839d-cc46eb0d16ff).

**High Agreement, Shallow Reasoning: A Mixed-Method Study of LLMs in Refactoring Reviews — Amorim et al., PROMISE 2026.** The study reports high agreement on 146 Java refactoring pairs, but its sampling retains human-approved refactorings and its operational definition counts choosing the refactored version as alignment. Consequently, the headline agreement is not evidence that a model can distinguish safe refactoring from hidden behavioral changes; always choosing the refactored version would satisfy that definition. The refactored version is also always shown as "Code 2", so a preference for the second option cannot be separated from a real preference. The paper does not itself claim to detect behavioral changes; its pairs were validated as behavior-preserving, and the prompt asks only about clarity, readability and maintainability. The qualitative analysis finds context and reasoning failures, and each model runs only once per pair. **Implication:** our evaluation must include both harmless transformations and plausible-looking refactors containing consequential changes. [Paper, §§3.3–3.4, 4.2, 6](https://homepages.dcc.ufmg.br/~figueiredo/publications/promise2026preprint.pdf), [official program](https://conf.researchr.org/home/promise-2026).

### Attention, ordering and reviewer cognition

**Deep Learning-based Code Reviews: A Paradigm Shift or a Double-Edged Sword? — Tufano et al., ICSE 2025; preprint November 2024.** A controlled experiment with 29 experienced participants found that an initial automated review concentrated attention on the locations it named. Assisted reviewers identified more minor issues, but not more high-severity issues than manual reviewers. Time and confidence differences were not statistically significant. The experiment used Java/Python programs with injected issues, so its results do not directly establish the effects of collapsing production PRs. Nevertheless, attention narrowing is directly relevant to hiding code. **Implication:** measuring how much code disappears is insufficient; evaluate consequential issues missed in the collapsed portion and whether reviewers independently examine it. [Official conference entry](https://conf.researchr.org/details/icse-2025/icse-2025-research-track/72/Deep-Learning-based-Code-Reviews-A-Paradigm-Shift-or-a-Double-Edged-Sword-), [author manuscript, §§II–IV](https://arxiv.org/html/2411.11401v3).

**On the Optimal Order of Reading Source Code Changes for Review — Baum, Schneider and Bacchelli, ICSME 2017.** Twelve interviews and a survey of 201 developers produce a theory of how to order change parts for review: group related parts as closely as possible; provide information before it is needed; when the two conflict, prefer grouping; treat closely related parts as chunks; the closest distance is "visible on the screen at the same time"; and make the grouping explicit with rules the reviewer can understand. The theory rests on stated preferences, and the authors call it untested. Logs of 292 industrial review sessions show only that reviewers often follow the tool's order. The direction between a callee and its callers was subjective: interviewees leaned top-down, survey respondents bottom-up. The paper also keeps importance out of reading order. **Implication:** keep a changed definition with its uses rather than in a separate earlier section, and show why parts are grouped. [Paper, §§II–V](https://sback.it/publications/icsme2017.pdf).

**Associating Working Memory Capacity and Code Change Ordering with Code Review Performance — Baum, Schneider and Bacchelli, EMSE 24, 2019.** In an experiment with 50 participants reviewing seeded defects, working memory capacity had a small association with finding delocalized defects, those that need knowledge of several code parts (Kendall τ = 0.24), and almost none with other defects; review time mattered more. Smaller changes were reviewed more effectively, but the formal test covered one defect type and the cause is open. Orderings derived from the 2017 theory showed no significant effect: the best order that kept files whole found 59% more defects per hour than the worst (p = 0.11), and in the comparison that allowed files to be split, the means pointed the other way, which the authors call "a possible contradiction to the theory". **Implication:** folding one part of a decision hides exactly the context delocalized defects need, and grouping across files is a hypothesis to test, not an established benefit. [EMSE preprint](https://zenodo.org/records/2001923).

**First Come First Served: The Impact of File Position on Code Review — Fregnan et al., ESEC/FSE 2022.** Alongside repository mining, a controlled experiment assigned 106 participants to different positions for two seeded Java defects. A corner-case defect had 64% lower detection odds when its file appeared last; the missing-break defect showed no significant position effect. This is an odds comparison for one defect, not a general percentage improvement in detection. **Implication:** ordering merits an experiment as an alternative or complement to folding. The study does not identify an optimal ordering algorithm or test LLM rankings. [Paper, §§3.3, 4.2, 5](https://eprints.gla.ac.uk/273443/3/273443.pdf), [institutional publication record](https://eprints.gla.ac.uk/273443/).

**Breaking the Alphabet: Rethinking File Ordering in Code Review — Rahman, Codabux and Roy, ICSE 2026, [DOI 10.1145/3744916.3787838](https://doi.org/10.1145/3744916.3787838).** A survey analyzed 1,355 responses from developers recruited through 182 projects and snowball sampling. In open-ended answers, respondents most often asked for dependency order (489 mentions, described top-down: interface, implementation, tests, then downstream changes), module grouping (452), links between related files (427) and priority by criticality (405). These are coded counts without a denominator. 63% supported customizable ordering. Some percentages in the abstract differ from the body; cite the body. The evidence concerns reported preferences and difficulties; it does not measure whether a new interface prevents missed bugs. **Implication:** a decision can link its contract, implementation, and tests without requiring the reviewer to reconstruct that relationship from the file list. [Paper, §§3, 4.6, 6](https://arxiv.org/pdf/2609.04207), [publication record](https://arxiv.org/abs/2609.04207).

**Does Order Matter? An Empirical Investigation into the Impact of File Ordering on Code Review Effectiveness — Rahman et al., September 2026 preprint.** Studies 330,343 multi-file PRs. Associations between position and later bug-fixing activity are small. Its defect label marks a file "latent buggy" when it appears in two consecutive PRs and the second is a bug-fixing PR, identified by commit-message keywords. The authors state this heuristic is not ground truth. It does not establish which change introduced a defect. Useful motivation for testing presentation order, not causal evidence that reordering prevents bugs. [Methods §4.4.2 and results §5](https://arxiv.org/html/2609.22610v1).

**The Effect of Complexity and Provenance on Code Review Decisions — Singh et al., FSE 2026 (PACMSE).** In a between-subjects experiment with 385 participants, higher code complexity significantly increased acceptance of incorrect suggested revisions; labelling a suggestion as AI- or human-written had no supported effect. **Implication:** stratify evaluation by complexity, where over-reliance is most likely. Abstract read. [Publisher record](https://doi.org/10.1145/3808165).

### LLM review in practice

**Rethinking Code Review Workflows with LLM Assistance: An Empirical Study — Aðalsteinsson et al., ESEM 2025 (Industry, Government, and Community Track).** A field study at WirelessCar compared upfront AI reviews with assistance requested during review. The experimental phase involved ten participants. Developers valued orientation and contextual explanations, but reported lengthy output, minor findings, missing architectural context, and friction from leaving familiar tools. Preferences depended on familiarity and review risk. The study is qualitative and comes from one company; it does not establish a measured productivity gain. **Implication:** keep the initial view short, attach file/line evidence, and make deeper explanation available on demand. [Publisher record](https://ieeexplore.ieee.org/document/11323409/), [author manuscript, §§IV–VI](https://arxiv.org/html/2505.16339v1).

**RovoDev Code Reviewer: A Large-Scale Online Evaluation of LLM-based Code Review Automation at Atlassian — Tantithamthavorn et al., ICSE 2026 SEIP.** A deployment across over 1,900 repositories generated over 54,000 comments. PRs receiving comments had a roughly 31% shorter median cycle time; the authors also analyze the rollout as an interrupted time series. Neither design randomly assigns comparable PRs to folding versus full review, so this is encouraging deployment evidence, not a causal speedup estimate for us. Offline ablations favor review guidelines and actionability filtering; their extra LLM factual-check stage adds little on the measured alignment metric. **Implication:** test additional model passes rather than assuming they improve quality. [Paper, §§3–6](https://arxiv.org/html/2601.01129), [official program](https://conf.researchr.org/details/icse-2026/icse-2026-software-engineering-in-practice/2/RovoDev-Code-Reviewer-A-Large-Scale-Online-Evaluation-of-LLM-based-Code-Review-Autom).

**Human-AI Synergy in Agentic Code Review — Zhong et al., March 2026 preprint.** The authors analyze 278,790 inline conversations from 300 projects. Agent feedback is more verbose and concentrates on improvements and defects; human feedback also covers understanding and knowledge transfer. Estimated suggestion adoption is 16.6% for agents versus 56.5% for humans. Adoption uses subsequent code changes and similarity, so an unadopted suggestion is not automatically wrong; alternative fixes account for some cases. This observational study does not isolate presentation effects. **Implication:** measure usefulness and understanding, and do not optimize for comment volume or treat ignored advice as a clean negative label. [Paper, §§II, III-A, III-C, V](https://arxiv.org/html/2603.15911).

**Automated Code Review In Practice — Cihan et al., ICSE 2025 SEIP.** Across 4,335 PRs, 1,568 with automated review, 73.8% of bot comments were resolved, but average PR closure time rose from 5h52m to 8h20m (p < 0.001). Practitioners worried reviewers would assume the bot had found every issue. **Implication:** measure end-to-end PR time, not only reading time. [Paper](https://arxiv.org/html/2412.18531).

**AI-Assisted Assessment of Coding Practices in Modern Code Review (AutoCommenter) — Vijayvergiya et al., AIware 2024.** At Google, a single global confidence threshold of 0.98 suppressed many correct predictions; about 80% of sampled predictions below it were still correct. The team moved to per-category thresholds. Suppressing 17 non-actionable categories raised the useful ratio from 54% to 66%. **Implication:** set visibility policy per label, and measure each label's misses separately. [Paper, §§4–5](https://arxiv.org/html/2405.13565).

**Automating Low-Risk Code Review at Meta: RADAR, Risk Calibration, and Review Efficiency — Adams et al., 2026 preprint.** Diffs pass through several layers before landing without human review: authorship and source gates, static heuristics, a trained risk score, an LLM review, and deterministic validation. The deployment reviewed 535K+ diffs and landed 331K+. RADAR diffs have a third of the revert rate of other diffs, but the comparisons are observational and the diffs were selected as low-risk. **Implication:** combine the model's judgment with rules it cannot override. Abstract read; the layered design is the transferable part. [Paper](https://arxiv.org/abs/2605.30208).

**Understanding the Limits of Automated Evaluation for Code Review Bots in Practice — Karakaya et al., accepted to EASE 2026 according to the authors' arXiv record.** On 2,604 industrial bot comments, automated judges agreed with developer fixed/wontFix labels only about 44–62%. Such actions also reflected organizational constraints. **Implication:** “ignored” is an ambiguous quality label when designing feedback. [Author manuscript](https://arxiv.org/html/2604.24525v1), [acceptance statement](https://arxiv.org/abs/2604.24525).

### Context and intent

**From Overload to Insight: Bridging Code Search and Code Review with LLMs — Rao, Vasilescu, and Holmes, FSE Companion 2025, Ideas, Visions and Reflections.** A close conceptual match: an assistant retrieves information from code, history, tests, and documentation, then presents change-specific insights. Its proposed prioritization groups similar changes, including refactorings, and related changes, including definitions and call sites. It proposes tailoring their presentation to reviewer familiarity. The paper describes a research vision, not a controlled evaluation. **Implication:** organize around connected behavioral changes and supporting evidence rather than assuming each file is an independent review task. [Author-hosted paper, Figure 1 and Table 1](https://cmustrudel.github.io/papers/fse2025nier.pdf), [official conference program](https://conf.researchr.org/details/fse-2025/fse-2025-ideas-visions-and-reflections/28/From-Overload-to-Insight-Bridging-Code-Search-and-Code-Review-with-LLMs).

**Benchmarking LLMs for Fine-Grained Code Review with Enriched Context in Practice (ContextCRBench) — Hu et al., FSE 2026 Industry; preprint November 2025.** The benchmark contains 67,910 entries, combining linked issue/PR descriptions with surrounding functions or classes. The model evaluation uses a stratified 1,080-entry subset and separates hunk assessment, line localization, and comment generation. Across eight tested models, textual intent context generally helped more than surrounding code alone; results vary by task and model family. Labels come from filtered historical reviews, including LLM filtering, and comment scoring uses text similarity. This does not prove that uncommented code is harmless. **Implication:** retrieve the requirement explaining a change, then evaluate selection, source localization, and explanation separately. [Official FSE program](https://conf.researchr.org/details/fse-2026/fse-2026-industry-papers/33/Benchmarking-LLMs-for-Fine-Grained-Code-Review-with-Enriched-Context-in-Practice), [author manuscript](https://arxiv.org/html/2511.07017v2).

**AACR-Bench: Evaluating Automatic Code Review with Holistic Repository-Level Context — Zhang et al., January 2026 preprint.** The benchmark covers 200 PRs from 50 repositories and ten languages, with 1,505 curated review comments. It compares diff-only, retrieval, and agent-based reviews. Extra context did not consistently improve results. In one tested setup, Claude 4.5 Sonnet's agent review achieved 39.90% semantic precision but 10.10% recall; this illustrates a tradeoff, not a general ranking of models or tools. The authors acknowledge incomplete ground truth. **Implication:** compare targeted retrieval against diff-only input, and measure missed issues alongside relevance when making the extension more selective. [Author manuscript, §§3–4 and Table 3](https://arxiv.org/html/2601.19494v3), [version/publication record](https://arxiv.org/abs/2601.19494).

**SWE-PRBench: Benchmarking AI Code Review Quality Against Pull Request Feedback — Kumar, March 2026 preprint.** The corpus contains 350 PRs; the reported model evaluation uses 100, with deliberate oversampling of context-dependent tasks. All eight tested models score lower with the paper's enriched input configurations than with the diff alone. This is evidence against assuming more context helps. It does not prove retrieval is harmful generally: the configurations use specific small budgets, selective context representations, a prompt targeting 4–6 findings, and model judges. There is no measured human baseline. **Implication:** compare specific evidence packages with the same model and task instead of installing broad retrieval on faith. [Paper, §§4–6, 8](https://arxiv.org/html/2603.26130).

**Measuring and Exploiting Contextual Bias in LLM-Assisted Security Code Review — Alexopoulos et al., 2026 preprint.** Six models reviewed the same vulnerable code under five framings. Stating that the code is secure collapsed GPT-4o-mini's detection from 97.2% to 3.6%. Other models lost 16–60 points; Claude Opus 4.5 lost 6.9. Against two real review pipelines, iteratively refined PR descriptions got vulnerability-reintroducing reverts accepted in 32 of 33 cases. Redacting the PR description restored detection in 16 of 32; also redacting commit metadata recovered 12 of the remaining 16. **Implication:** the pass that labels edits should not read author-written framing. [Paper, §§III–IV and Tables II–III](https://arxiv.org/html/2603.18740).

**Context-aware Code Summary Generation — Su et al., Journal of Systems and Software 231, January 2026; preprint 2024.** Uses summaries of callers to explain a method's purpose. Its human preference study concerns Java method summaries, not review selection or semantic equivalence. The preprint's introduction claims the small model "outperforms both Gemini and GPT-4". Its only direct comparison, against a Gemini configuration, is not statistically significant (p = 0.119, Table 4, Experiment 4), and it is never compared directly with GPT-4. The journal version's wording was not checked because the publisher page blocked access. **Implication:** explanations should state a method's role in a flow when caller evidence is available. [Journal paper](https://www.sciencedirect.com/science/article/abs/pii/S0164121225002493), [earlier author manuscript](https://arxiv.org/abs/2408.09006).

The context papers are not interchangeable replications. They use different tasks, models, evidence packages, and labels. Their combined lesson is to evaluate context selection, not to conclude that context always helps or always hurts.

### Reliability of model output

**Calibration and Correctness of Language Models for Code — Spiess et al., ICSE 2025; Are LLM Decisions Faithful to Verbal Confidence? — Wang et al., 2026 preprint.** Code models are poorly calibrated out of the box, with expected calibration error from 0.09 to 0.73; rescaling on labelled data helps. Separately, models rarely abstain, and prompting with explicit error penalties fails to induce abstention; those tasks are question answering, not code. **Implication:** keeping `unknown` edits visible depends on the model volunteering uncertainty, which it does unreliably. Behavioural signals, such as disagreement across repeated classifications, deserve measurement. [Spiess et al.](https://arxiv.org/html/2402.02047), [Wang et al.](https://arxiv.org/html/2601.07767v1).

**Hallucinations in Code Change to Natural Language Generation — Liu, Lin and Thongtanunam, IJCNLP-AACL 2025.** Across 1,596 annotated outputs from fine-tuned 7–8B models, 42.8–47.0% of generated review comments and 14.2–21.6% of commit messages contained hallucinations; a recurring pattern was claims about entities absent from the diff. Single automatic metrics are weak detectors; combinations do better. **Implication:** explanation correctness needs human annotation in our evaluation. [Paper, §§3–5](https://aclanthology.org/2025.ijcnlp-long.137.pdf).

**A Preliminary Study on Explaining Risk of Code Changes using LLM-Based Prediction Models — Liu et al., AIware 2026.** Attention from Meta's diff risk model highlighted top-K units of expert-labelled outage-causing diffs. The top two hunks covered the culprit lines 53.85% of the time while showing 26.28% of changed lines; the top three files reached 92.30% while showing 78.61%. **Implication:** report coverage of consequential lines against the share of lines left visible, at several granularities. [Paper, Table 1](https://arxiv.org/html/2607.02782).

**CodeReviewQA: The Code Review Comprehension Assessment for Large Language Models — Lin et al., Findings of ACL 2025.** Assesses change-type recognition, localization, and solution identification through 900 curated examples across nine languages. Useful for separating comprehension failures; its multiple-choice task does not measure whether a human reviewer can safely skip code. [Publisher record and paper](https://aclanthology.org/2025.findings-acl.476/).

**From Static to Dynamic: Benchmarking Real-World Code Review with MCR-Bench — Zheng et al., accepted to ISSTA 2026 according to the authors' arXiv record.** The August 2026 manuscript covers 2,269 multi-round tasks with defect-state labels and reports difficulty tracking defects over successive revisions. Relevant to re-analysis after new commits; it does not evaluate focused-diff interfaces. [Author manuscript](https://arxiv.org/html/2608.27442v1), [acceptance statement](https://arxiv.org/abs/2608.27442).

### Surveys

**A Roadmap for Modern Code Review: Challenges and Opportunities — Yang et al., ACM TOSEM 35(9), pp. 1–42, published 21 August 2026; article number unverified.** A broad synthesis of 2013–2025 research, including change understanding and prioritization. Useful for terminology and further references, rather than direct evidence for this extension. Bibliographic details and abstract were accessible in indexed publisher text; direct publisher opening failed. [Publisher record](https://doi.org/10.1145/3800963).

## Assessment of our choices

| Choice | Assessment | Next question |
| --- | --- | --- |
| Separate classification from prioritization | A defensible, auditable architecture; not proven optimal. Beyond Summaries evaluates a related but different pipeline. | Does staging reduce consequential omissions compared with one request on the same evidence? |
| Classify from code alone | Removes a demonstrated framing attack surface from the labelling pass. Loses intent hints that might resolve ambiguous edits. | Does classification accuracy change on PRs with accurate descriptions, and hold on PRs with misleading ones? |
| Group changes by a review decision | Fits reported needs for relationships and orientation. | Can a reviewer follow the implementation and relevant tests without reconstructing the explanation? |
| Explain what changed and why it matters | Supported by workflow evidence, provided the explanation is correct and quick to verify. | Does reading and checking the explanation save net effort? |
| Fold supporting code | Plausible and reversible, but the highest-stakes unvalidated choice. Review decisions now keep all their changed lines. | Does folding cause reviewers to miss consequential decisions or the evidence needed to assess them? |
| Keep `unknown` edits and protected paths visible | Useful rules the model cannot override. `unknown` depends on the classifier admitting uncertainty, which calibration research suggests it does unreliably. | Which important edits receive an unjustifiably ordinary label and still fold? |
| Remove fixed presentation quotas | Matches the product objective. None of the reviewed evidence establishes an ideal universal line count. | Can we preserve all important evidence while removing repetition? |
| Read the included PR jointly before selecting decisions | Enables cross-file reasoning. The global stage also delays the first finished explanation. | Compare quality, time to first useful explanation, total latency, and result revisions against provisional per-file delivery. |
| Exclude generated files by default | A user-selected scope policy, not a research finding that generated changes are harmless. | Keep excluded files separate from analyzed supporting changes in evaluation and coverage reporting. |

**The correctness of a reference is different from the correctness of its explanation.** A source excerpt can exist, cite a real changed line, and still omit the guard that changes its meaning. Our validators check the former; the latter needs semantic evaluation. Count both missing decisions and insufficient evidence for otherwise-present decisions. None of the works reviewed here establishes that an LLM's omission is reliable evidence that code has no behavioral effect.

## What to investigate next

These are proposed experiments and design directions, not results the studies establish.

**First, evaluate the collapsed remainder.** Build a small, fixed set of maintainer-labelled PR revisions before tuning the prompt further. Include a genuine move, a move with a subtle condition change, a serialized rename, a caller/callee contract change, a test that weakens an assertion, and a dependency change. Add PRs whose descriptions misdescribe a behavior change, and seeded defects that span a shown decision and a supporting edit. These are proposed test cases, not observed PRiorities failures. Use human labels independent of the model's first answer. The attention findings make this a higher priority than maximizing the hidden-line percentage. [Tufano et al.](https://arxiv.org/html/2411.11401v3), [Baum et al.](https://zenodo.org/records/2001923), [Alexopoulos et al.](https://arxiv.org/html/2603.18740).

**Then test targeted evidence.** Compare the current capture with small, explicitly connected evidence packages: enclosing scope, relevant caller or callee, related assertion, and requirement text when available. Record why each source matters and pin it to the PR revision. Begin with manually prepared packages, so we can find whether the missing evidence changes decisions before building retrieval infrastructure. CodeGraphContext could later supply such evidence; the papers do not establish that this particular backend improves our task. [ContextCRBench](https://arxiv.org/html/2511.07017v2), [SWE-PRBench](https://arxiv.org/html/2603.26130).

**Measure uncertainty from behavior, not only self-report.** Run classification repeatedly on the same evidence and record where labels disagree. If disagreement predicts edits that maintainers say must stay visible, it could join `unknown` as a visibility rule. [Spiess et al.](https://arxiv.org/html/2402.02047).

**Try structural comparison on move-heavy cases.** Align old and new code so a reader can inspect what changed during the move. Start as an evaluation condition, not a mandatory parser dependency. A detector's move or rename label is still fallible, and structural similarity does not establish equivalence. [RAID](https://homepages.dcc.ufmg.br/~mtov/pub/2021-icpc.pdf), [Someya et al.](https://arxiv.org/abs/2508.11993).

**Keep orientation compact.** Prefer one useful behavioral explanation and a concrete review question, with the existing detail and source controls providing depth. Compare a guided sequence of related decisions with native file order. Avoid assuming that more explanation is better; its verification time belongs in the cost. [Workflow study](https://arxiv.org/html/2505.16339v1), [file-order experiment](https://eprints.gla.ac.uk/273443/3/273443.pdf).

An independent pass that audits only deferred changes is another candidate, but not an automatic next feature. The existing prompt already requests reconsideration. A second call must demonstrate enough additional recall to justify its latency and noise; RovoDev's ablations caution against treating an extra judge as inherently beneficial. [RovoDev, §5.3](https://arxiv.org/html/2601.01129).

## How to determine which approach is better

Start with a discovery pilot of roughly 20–30 varied PRs, followed by a human comparison sized using the pilot's variance. That count is a practical starting point, not a statistical guarantee. Include small and large changes, familiar and unfamiliar code, clean refactors and mixed changes, and varying complexity. Preserve base/head commits, captured context, provider, model, effort, and prompts. Keep prompt-development PRs separate from held-out evaluation PRs. Synthetic tangled PRs, built by combining atomic commits, can supply extra ground truth for decision grouping. [ColaUntangle](https://arxiv.org/html/2507.16395).

For ground truth, ask two maintainers to inspect the full evidence independently before seeing PRiorities output, then reconcile disagreements. Record each consequential decision, whether it would affect approval, the source needed to assess it, and unresolved context. Historical comments can seed this work but cannot define the complete set: uncommented code is not a negative label. Measure valid behavior changes and comprehension, not just defects. [AACR-Bench's annotation motivation](https://arxiv.org/html/2601.19494v3).

Separate the interface comparison from the model-pipeline comparison. The first three conditions map to the extension's **Full diff**, **Explained** and **Folded** views, which reuse identical model output:

| Interface condition | What it isolates |
| --- | --- |
| Native full diff | Baseline review behavior. |
| Full diff with PRiorities explanations | Value and cost of orientation without folding. |
| Same explanations with PRiorities folding | Additional effect of collapsing code. |
| Same evidence arranged as connected review decisions | Effect of navigation and order, if the first comparison warrants a further prototype. |

Assign different PRs to each condition for a given participant, balance their order, and distribute each PR across conditions among different participants. Seeing the same bug in an earlier condition would contaminate the comparison. Include codebase familiarity and code complexity in the analysis. Presentation should use fixed outputs; evaluate repeated model runs separately to expose selection instability.

Measure:

- **Consequential omissions:** maintainer-labelled decisions absent from the focus, and present decisions whose necessary evidence is initially hidden; report by severity and PR type. Plot coverage of consequential lines against the share of changed lines left visible, at line, hunk and file granularity. [Liu et al.](https://arxiv.org/html/2607.02782).
- **Human outcome:** important decisions found, correct understanding of the behavior, and whether participants notice concerns the model missed.
- **Explanation correctness:** human-annotated false or unsupported claims, since automatic detectors are weak. Inspect errors separately: selection of the wrong change, insufficient context, incorrect reasoning, and evidence pointing at the wrong source. [Liu, Lin and Thongtanunam](https://aclanthology.org/2025.ijcnlp-long.137.pdf).
- **Noise and effort:** irrelevant explanations, active review time including explanation verification, expansion and navigation effort, and perceived workload. Expansion alone is not failure; it may be appropriate investigation.
- **Operational cost:** model usage, total completion time, time to first useful explanation, end-to-end PR time, and variation across repeated runs. [Cihan et al.](https://arxiv.org/html/2412.18531).

Report uncertainty and individual serious misses, not only an average score. Zero observed critical misses in a small pilot does not prove zero risk. Agree on an acceptable quality difference before looking at comparative results. If folding saves scrolling but increases consequential misses, that is a failed result for the product. If explanations deliver the benefit and folding adds none, retain the evidence for changing the default.

After fixing the interface condition, compare one-pass selection, staged classification/prioritization, and staged analysis with targeted evidence on the same held-out PRs. An optional omission audit can form a later ablation. Do not change models, prompts, retrieval, and layout simultaneously and attribute the result to any one of them.
