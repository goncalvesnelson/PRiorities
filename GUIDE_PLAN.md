# PRiorities Guide implementation plan

Implementation authorized on September 30, 2026, including the article-informed content adjustment below. The user selected option B: **Full diff** and **Guide** are the main views, with a folding control inside Guide. Reading order follows comprehension, introducing prerequisites before their uses. Folding focuses on the current section and links to other sections whose edits are collapsed. The user also requested before/after code together and confirmed one review checkbox per continuous changed block, with all blocks checked completing the file. Real-output evaluation will determine whether short navigation labels or per-file role notes are needed. Production implementation and automated verification are complete. The fresh-reader comparison remains outstanding; the earlier repeat readings do not establish a speed improvement.

The goal is to make a pull request easier to understand and review through an accurate guided walkthrough. A reviewer should understand what changed, why it matters, what needs their judgment, and where the evidence is. Wording, grouping, reading order, and code selection determine success alongside layout. Every change must remain inspectable. Clear prose does not compensate for unsupported or incorrect claims.

References: [Linear Guides](https://linear.app/docs/diffs#guides), [Linear's review workflow](https://linear.app/now/reviewing-code-in-the-agent-era) (June 10, 2026), [LinearB's review advice](https://linearb.io/blog/how-to-do-code-reviews-better) (March 17, 2022), [PR #477](https://github.com/uphold/portfolio-service/pull/477), and the [navigation comparison](output/pr-477-view-options-preview.html). The #477 mockups contain hand-written explanations; they are design references, not evidence of current model output quality.

The LinearB article recommends supplying context, limiting review workload, asking constructive questions and measuring outcomes. Our application of that advice is to introduce intended behavior before asking for judgment, keep the implementation and its dependencies together, and ask concrete questions beside the relevant code. Its workload heuristics do not establish useful Guide section boundaries or justify fixed line quotas. Review checkboxes record human inspection, not approval or an AI claim that code is safe. Treat these as design choices to evaluate against the reader's experience, not proof that the Guide improves review quality.

Linear's workflow article describes understanding the motivation, surveying the diff, then using a narrative walkthrough for larger changes. The agreed content adjustment is to name sections by the behavior they explain, carry each mechanism through its implementation and callers, and place review concerns after that explanation. Full diff remains directly accessible. The article does not disclose its chunk-selection algorithm or validate ours. Its author's reliance on agents for correctness is not a reason to relax the demonstrated need for claim verification here. The revised-prompt experiment is the first implementation gate.

   **Decision C confirmed: per-section visibility.** Keep the current section's assigned edits and evidence visible. Fold other sections' edits with links to their owning sections, even when those edits have review priority. Opening a supporting section also reveals its own assigned edits, regardless of whether the model supplied excerpts.

   The visibility rule for a captured code row is explicit: keep it if it belongs to an edit assigned to the current section, lies within one of that section's selected excerpts on the matching before/after side, belongs to an unresolved or user-selected always-visible edit, or lies in a protected file. When a selected excerpt intersects a changed block, show that whole block with both its removals and additions together. Fold all other captured code rows into contiguous runs; keep hunk headers and omitted-range markers legible. Unchanged context stays open only through the section's excerpts or file protection. Do not add an arbitrary surrounding-line allowance or infer extra context during rendering. If the selected context is insufficient, record that failure in the content evaluation and address the evidence selection.

   Label every visible run of edits owned by another section with a link to that section and the reason it remains visible, such as “Section D — unresolved evidence”, “Section D — your always-visible types”, or “Section D — protected file”. If the current section's excerpt includes another section's edit, label it as selected evidence from that section. Group adjacent rows only when ownership and visibility reasons agree; preserve all applicable reasons when overrides overlap. Unchanged protected context has no edit owner: label it as protected context rather than assigning it to a section. These labels must remain available without hovering. Folded edits likewise identify their owning sections; another section's review edits must not be described as low-priority supporting code.

   The folding checkbox starts enabled, matching the mock. Turning it off shows every captured diff row in the selected section's files; each hidden run can also expand independently. Adjust the checkbox wording to describe section focus rather than lower importance, for example **Fold other code**. Supporting topics may lack a question or excerpts; omit empty prose fields while showing their assigned code.

   Show an overview of every section in comprehension order, with each section's supplied review/supporting priority visible. This lets the reader find judgment calls that occur later in the sequence without reordering the walkthrough. Keep a PR-level unresolved-evidence count with routes to affected sections. No fixed section count applies; select the first section in the agreed reading order and provide both overview navigation and Previous/Next controls.

4. **Implement the agreed content and Guide behavior.**

   After the decisions above, render sections from `analysis.topics`, using the agreed reading order. Each edit belongs to exactly one topic; different edits in the same file may belong to different sections. A shared file may consequently appear more than once. Do not derive sections from `buildReviewGroups()`, which assigns each file to its earliest group.

   Present the section overview and the selected section's title, before/after behavior, consequences, supplied review question, code, and specific evidence limits. Add file-role notes, short labels, or more precise statement-to-source links only according to the evaluated and agreed content contract. Keep classification details and provenance secondary. Preserve edit-level uncertainty even when the topic's prose omits it. Mark an all-supporting result honestly and keep all its sections accessible.

   Render captured diffs and any cited unchanged source with verified paths, line numbers, and before/after sides. Keep each file in one panel per section, with removals and additions together in a unified diff; do not render separate before and after excerpt cards for the same change. Merge overlapping excerpts and preserve original diff order. Source outside the diff remains distinguishable from diff rows. Show omitted ranges explicitly. Folding controls captured rows; it does not fetch or imply inspection of unavailable repository source.

   Place explanations beside code on wide screens and above it on narrow screens. Support GitHub themes, keyboard navigation, Previous/Next, and stable focus when content updates. Keep the selected section and expansion choices when returning from Full diff.

   **Block review requested by the user:** one checkbox covers one continuous changed block, including its before and after rows. Use captured edit identity rather than model topics or excerpt ranges, so the same block shares one checked state across sections and overlapping excerpts. File headers show reviewed blocks out of every changed block in that file, including blocks outside the current section, with a route to remaining blocks. Checking every block marks the whole file Viewed through GitHub's control; unchecking a block makes the file incomplete again. Looking at a section, opening a fold, or finishing model analysis never checks a block. Incomplete capture or absent block data must not imply a reviewed file.

   This replaces the earlier prohibition on automatic Viewed changes: the trigger is the user's explicit block checks. GitHub remains the record of file-level completion; partial progress belongs to the block checklist. A checked block records inspection only; it does not resolve a comment, approve the PR or assert correctness. Confirmed synchronization: persist partial block progress across reloads and tabs for the same PR and captured commits, independently of the AI assessment cache. Reset progress when the commit pair or captured block identity changes. Manually checking native Viewed checks every block; manually unchecking it clears every block. When the native control is unavailable, retain completed block checks, show Viewed as pending, and apply the requested state when the control loads. Never present a pending native save as completed; report save failures without discarding inspection progress. `reviewToggle(path)` is a toggle, so implementation must check the current native state before invoking it. Marking a file Viewed must not remove access to a multi-file explanation.

   The untimed [interactive mock](output/guide-evaluation/pr-5881-guide.html) demonstrates paired code and block progress using the original #5881 analysis. Its checkboxes are in-memory preview state and do not update GitHub. The timed evaluation pages retain their original presentation and saved results.

   Implementation proposal for the file list: keep captured GitHub file order, existing status filters, and Retry file/Review anyway actions; remove its review-group headings because section navigation now provides that grouping. Add links from each file to every section explaining its edits, reusing `fileTopics(path)`. That helper currently maps edit ownership only; distinguish any additional sections that cite the file solely as evidence, deriving those references from their excerpts. A link selects the section and brings that file's code into view. Generated and unanalyzed files remain reachable even when they have no topic. Keep progress, errors, and Settings accessible in both views.
